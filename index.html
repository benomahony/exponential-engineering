1

the treadmill

Your agent writes a bug. You spot it. You say "please don't do that". It fixes it.

I swallowed an exception with a bare except: pass
fixed! ✨

Next week, a different session, a different file:

I swallowed an exception with a bare except: pass

You fixed the instance.
The category is still alive.

Agents don't remember last Tuesday. Your codebase does.

2

the big idea

When you find a mistake, don't fix it.
Fix every future version of it.

Ask one question:

"What rule would have caught this automatically?"

Then write that rule. Lint it. Run it everywhere.

It's kaizen for codebases that are written by robots. Toyota called it poka yoke: mistake proofing. Make the wrong thing impossible, or at least loud.

3

the loop

  1. spot a mistake in a diff, a review, an incident
  2. name the category, not the line
  3. encode it as a deterministic check
  4. run it in the editor, the hook, the CI
  5. let the agent self correct from the error message

↺ forever

Each lap is small. Five minutes. One rule. The point is that you never run the same lap twice.

4

why exponential?

A fix touches one line.

A rule touches every line written by every agent in every session, forever.

Rules compound like interest. Your agents get better without getting smarter, because the space of wrong answers keeps shrinking.

5

the enforcement ladder

Not all "rules" are equal. Climb as high as you can.

  1. unrepresentable types make it impossible
  2. type checker fails the build
  3. lint rule fails with a fix hint
  4. test catches it after the fact
  5. review comment catches it sometimes
  6. AGENTS.md prose: a polite wish

Prose in a prompt is a suggestion. A failing check is a fact.

6

anatomy of a good rule

The error message is the prompt. The agent reads it and fixes itself.

error: banned import

😐 the agent guesses

error: `pandas` is banned.
  Use duckdb for SQL style queries
  or polars for dataframes.
  See docs/data.md

😎 the agent knows

  • says what is wrong
  • says what to do instead
  • points where to read more
  • is deterministic: same input, same answer
7

real rules, real cheap

Ban a library with ruff:

[tool.ruff.lint.flake8-tidy-imports.banned-api]
"pandas".msg = "Use duckdb or polars instead."
"requests".msg = "Use httpx with a timeout."

Ban a pattern with ast-grep:

id: no-print-in-lib
language: python
rule:
  pattern: print($$$ARGS)
message: Use the logger from app.log, not print().
severity: error

Most mistakes are already a rule someone wrote. Turn it on before you write your own.

8

where rules live

Run them where the agent will trip over them fastest.

editorLSP squiggles as it types
agent hooklint after every edit, feed errors straight back
pre commitnothing broken gets saved
CIthe backstop that never sleeps

The shorter the loop, the less the agent wanders off building on a broken idea.

9

careful now

  • noisy rules are bugs. A false positive teaches agents (and humans) to add noqa everywhere.
  • prune. Hundreds of prose rules make agents follow fewer of them. Lint rules only speak when broken, so they scale. Prose doesn't.
  • escape hatches need reasons. # noqa: BLE001 retry loop logs it
  • don't make an LLM your linter. Pass or fail, every time, for free.
10

try it monday

  • keep a "that again?!" list for one week
  • for each entry, find an existing lint rule
  • no rule exists? write one with ast-grep or semgrep
  • wire lint into your agent's post edit hook
  • make CI fail on it
  • delete the matching line from AGENTS.md 🎉

Every mistake is a gift.
Unwrap it once.
